当前句索引本身不够精确
句子很短/很密时，上一句下一句的定位会更飘
所以现在真正的问题有两个：

SkipBack / SkipForward 按钮接错了逻辑
现在是时间跳转，不是句子跳转
句子定位数据不完整
只有 start，没有 end，高亮和句子边界判断比较粗
如果你想实现真正稳定的“上一句 / 下一句”，正确做法应该是：

先根据 currentTime 算出当前句 activeIndex
点上一句：
跳到 segments[activeIndex - 1].start
点下一句：
跳到 segments[activeIndex + 1].start
最好后端再补 end 或 startSeconds/endSeconds
这样当前句判断会更准

## 后续：上一句 / 下一句 已按 P0 决策砍掉（2026-09-19）

上面记录的「上一句 / 下一句」两个缺陷**不再修复，改为直接删除**。理由：

1. **它是坏的，而且用户不知道它坏**：按钮在，点了也能跳，但跳的是「按时间估算的位置」
   而不是句子位置。这种「看起来能用、实际不准」的功能比没有更伤信任。
2. **它依赖的数据现在有了，但它本身仍不是 P0**：本地 Whisper 改造后
   `word_timestamps=True` 已经给出词级 start/end，`end` 字段是可以补齐的——
   所以它是「可修复但优先级不够」，不是「不可修复」。
3. **P0 目标是「能上传、能转写、能看、能存」**：单句循环、上/下一句、RSS 导入、
   导出 Anki/Excel/Markdown、分享死按钮一并砍掉，先把主链路跑通。

同时砍掉的还有**单句循环（含循环次数选择）**——它和上/下一句共用同一套
`loopRange` / `loopSentenceIndex` 状态，一起删除才能让播放器回到干净状态。

**如果将来要重做，正确的起点是**：先让后端把每段的 `end`（或
`startSeconds` / `endSeconds`）写进 `segments` 表，前端再用
`segments[i].startSeconds` 做高亮与跳转——而不是继续用
`currentTime >= parseTimeToSeconds(start)` 这种反推。
